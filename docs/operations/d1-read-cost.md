# D1 读取成本

D1 按**扫描行数**计费（`meta.rows_read`），不是按返回行数。Workers Free 套餐每天只有 500 万行读取、10 万行写入，UTC 00:00 重置；超出后所有查询直接报错，包括客户前台。

## 2026-10-02 事件与优化

两条读取各自把十几个 `catalog_runtime_*` 视图物化后，再对每个 SKU 逐行联表。SQLite 对每个 SKU 把这些物化结果整个扫一遍，读取行数随 SKU 数平方增长：

| 读取                           | 645 个 SKU 时每次读取行数（优化前） | 优化后（切换前 / 切换后） |
| ------------------------------ | ----------------------------------- | ------------------------- |
| 公共目录 `/catalog*`（含详情） | 约 173 万                           | 约 7 千 / 约 3 万         |
| 后台“管理所有产品”列表         | 约 84–87 万                         | 约 6.5 千 / 约 2.9 万     |

优化前每天只能打开 3–4 次页面就会耗尽 Free 额度。

做法：每个视图只读一次（`WHERE import_id = 当前基线`），在内存里按键合并（`readPublicCatalogRows`、`readManagedSkuRows`）。所有连接键在同一基线内唯一，所以结果与旧联表逐行一致，包括顺序。旧 SQL 原样保留在 `test/fixtures/legacy-*-sql.ts` 作为对照基准。

## 按需读取与共享缓存

- 分类页和产品族页只读该分类的产品类型：跳过其他类型的规格视图，销售、图片、价格三张共用视图按该类型的 SKU 过滤。
- 前台页面（目录首页、分类、产品族、Build a Hose、产品资源接口）使用 `sharedCache`：同一隔离实例内按 D1 绑定缓存已加载的商品，每次请求先读一次几行的新鲜度令牌（Active 指针版本、条目模式与 generation、切割贴标费率），令牌不变才复用。任何条目修订、删除、旧版发布或费率修改都会让令牌变化，下一次请求即重新读取。缓存的商品对象被冻结，调用方不能修改。
- 询价、报价和后台不使用共享缓存，仍按请求读取（`cacheItems` 只在同一请求内去重）。

基于预览数据（645 个 SKU）的每次请求读取行数：

| 场景                   | 切换前    | 切换后（条目模式） |
| ---------------------- | --------- | ------------------ |
| 全部商品，冷读取       | 7,402     | 30,024             |
| 单个分类，冷读取       | 1.2k–6.8k | 5.5k–21k           |
| 任意前台页面，缓存命中 | 3         | 3                  |

## 配置器“可选 End A”（Build a Hose）

选择胶管后列出 End A 选项的查询原先通过 `catalog_available_assembly_combinations` 得到“出现在可用总成中的兼容关系”，该视图对胶管的每个派生组合（例如 4,625 个）都去扫整张兼容关系视图和 SKU 视图，单次读取约 612 万行，一次请求就超过 Free 套餐全天额度。

现在一次 batch 只读该胶管的组合、兼容关系、相关部件的状态、接头与管套、停用记录和不可用胶管，在内存里按原视图的规则判定，并按原 SQL 的顺序输出（`readCompatibleEndARows`）。旧 SQL 原样保留在 `test/fixtures/legacy-compatible-end-sql.ts` 作为对照。预览数据上 26 次对照（两种模式各 13 个胶管）结果完全一致：

| 胶管        | 优化前（切换前 / 切换后） | 优化后          |
| ----------- | ------------------------- | --------------- |
| `601R1_004` | 613 万 / 618 万           | 1.6 万 / 2.0 万 |
| 无可选接头  | 5.4 千 / 1.0 万           | 110 / 2.3 千    |

“已选定两端”的读取（报价准备）和组合存在性检查原本就只读几千行，未改动。

## 2026-10-02 前后台补充扫描

扫描范围为 `app/modules` 的 18 个模块及 `workers`：检索数据库读取、循环内读取、运行时视图联表、分页、浏览器轮询和定时任务，并抽查前台目录/配置器/询价、客户消息、后台产品/审核/订单/通知和盘点路径。此记录不是每个页面在真实业务规模下的压测结论。

本轮补充优化：

- 客户消息列表先按原有个人/组织访问规则确定可见询价，再计算这些询价的最新消息；不再给所有客户的消息历史计算窗口排序。未读、附件、分页和组织授权规则不变。
- 目录切换盘点使用 `rowid` 游标分页，替代每页重新扫描前面记录的 `OFFSET`。保留每 1,000 行的哈希分块与顺序；游标用字符串保存，避免 JavaScript 对大整数 rowid 的舍入。
- 后台通知角标的焦点事件、可见性事件和定时器共用请求进行中状态，避免并发重复读取；组件卸载时取消未完成请求。保持原有刷新周期和权限检查。
- 前台目录只立即加载前 3 张商品图，其余交给浏览器按视口延迟加载；后台订单列表图片也延迟加载。实际请求数量取决于视口与浏览器，不把 `loading="lazy"` 当作确定的请求数上限。

验证边界：目录/后台产品按视图一次读取、目录版本缓存和配置器 End A 查询优化是此前已合入的改动，本轮做回归验证，不重复算作新增成果。询价提交和交易计算保留实时读取，历史快照保留原样，不引入跨用户业务数据缓存。

补充守护：`message-center-d1.integration.test.ts` 加入 1,200 条其他客户消息后，可见结果不变，读取增量低于 100 行；`catalog-cutover-d1.integration.test.ts` 在 5,002 条含负数、稀疏及超出 JS 安全整数范围 rowid 的记录上逐页对照旧查询，游标扫描低于 5,100 行，旧 OFFSET 扫描超过新方式 3 倍；`admin-navigation.test.tsx` 验证多个刷新事件合并与卸载取消。

后台询价审核追加优化：审核状态在 SQL 中筛选，普通“最新提交”列表每页返回 25 条，并多取 1 条判断下一页；技术审核上下文和历史只读取本页请求。页面可见时每 30 秒刷新，隐藏时暂停，手动、焦点和可见性刷新共用进行中状态。页面指标明确标为本页统计。

技术状态依赖修订指纹和当前草稿内容，因此指定技术审核筛选或“技术审核优先”排序时，仍对审核状态筛选后的整个候选集合计算，再分页，避免遗漏后续页面中的匹配项。SQL 的 LIMIT 只限制返回集合，不保证数据库仅扫描 26 行；普通路径仍需排序，深页 OFFSET 的成本也会增长。

`admin-quote-pagination-d1.integration.test.ts` 使用 76 条含相同提交时间和不同技术状态的请求，验证分页合并与全量结果一致、筛选和排序跨页正确，并断言普通首页读取量低于全量读取；`admin-quote-pagination-ui.test.tsx` 验证翻页保留筛选、刷新间隔、隐藏暂停和重复事件合并。

仍需按业务增长持续观察：管理产品及编辑器仍有全量投影；后台消息列表的最新消息排序面向所有对话。这些路径应在数据增长后按真实 D1 读取量决定是否增加服务端分页或专用摘要。不要仅为了减少请求而缓存管理员权限、交易金额或放宽消息访问范围。
